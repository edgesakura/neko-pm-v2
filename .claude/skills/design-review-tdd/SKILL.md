# Design-Review-TDD ワークフロー

実装タスクを受けた時に自動で品質ゲートを通すフロー。
「バカみたいなバグで動かないコードを乱発しない」ための仕組み。

## トリガー

- 新機能の実装依頼
- UI/UXの改修依頼
- リファクタリング依頼
- `/design-review-tdd` コマンド
- 3ファイル以上の変更が見込まれるタスク

## フロー概要

```
Phase 1: 設計
    ↓
Phase 2: タヌキレビュー（Codex）
    ↓
Phase 3: レビュー反映
    ↓
Phase 4: TDD（RED → GREEN）
    ↓
Phase 5: ビルド検証
    ↓
Phase 6: デプロイ（ご主人承認後）
```

## Phase 1: 設計

### TAP（思考増幅）を実施
CLAUDE.md の TAP プロトコルに従い、5拡張を行う。

### 専門家ペルソナを適用
タスクの性質に応じた専門家視点で設計を深める。

| タスク種別 | ペルソナ | 重視する観点 |
|-----------|---------|-------------|
| モバイルUI | モバイルシニアエンジニア | 44px タッチターゲット、thumb zone、Progressive Disclosure、No Nested Scroll |
| API設計 | バックエンドアーキテクト | RESTful原則、エラーハンドリング、べき等性、レート制限 |
| DB設計 | データベーススペシャリスト | 正規化、インデックス戦略、N+1問題、マイグレーション |
| インフラ | SRE | 可用性、コスト、スケーラビリティ、障害復旧 |
| セキュリティ | セキュリティエンジニア | OWASP Top 10、入力検証、認証/認可、暗号化 |

### 設計成果物
- 変更対象ファイルのリスト
- 各コンポーネントの仕様（入出力、振る舞い）
- テストケース一覧（TDD Phase で使う）

## Phase 2: タヌキレビュー

設計をそのまま実装に流さない。Codex（タヌキ）に投げて穴を探す。

### レビュー依頼テンプレート

```
codex-agent に以下を投げる:

## 設計レビュー依頼
[設計内容をここに記載]

## レビュー観点
1. この設計に穴はないか？
2. エッジケースの見落としはないか？
3. パフォーマンス上の問題が残る可能性は？
4. アクセシビリティの考慮は十分か？
5. 代替アプローチとの比較で劣る点はないか？
6. 実装時にハマりそうな落とし穴は？
```

### レビュー結果の分類

| レベル | 意味 | 対応 |
|--------|------|------|
| **Critical** | 設計変更が必要 | Phase 3 で必ず反映 |
| **Warning** | バグ/体験問題の可能性 | Phase 3 で検討、原則反映 |
| **Info** | 改善提案 | ご主人判断で取捨選択 |

## Phase 3: レビュー反映

1. Critical/Warning を設計に反映
2. Info はご主人に提示して取捨選択を仰ぐ
3. 反映後の設計を最終版として確定

**重要**: レビュー結果を無視して先に進まない。Critical が1つでもあれば設計を修正する。

## Phase 4: TDD

### テスト先行の原則
1. テストファイルを書く
2. テスト実行 → **RED（失敗）を確認**
3. 実装を書く
4. テスト再実行 → **GREEN（全パス）を確認**
5. リファクタ（テストが GREEN のまま）

### タスク分解とチーム編成

3ファイル以上の変更がある場合:
1. 依存関係を分析してタスクを分解
2. 独立したタスクを並列実行可能な子猫にアサイン
3. 依存するタスクは blockedBy で順序制御
4. 全タスク完了後にビルド検証

### テスト要件
- 改修対象コンポーネントのカバレッジ 80% 以上
- ユーザー可視の振る舞いをテスト（実装詳細ではない）
- エッジケース（空、null、境界値）を含める
- ARIA/アクセシビリティのテストを含める

## Phase 5: ビルド検証

全テスト + 型チェック + ビルドの3段階:

```bash
# 1. テスト
npx jest --coverage

# 2. 型チェック
npx tsc --noEmit

# 3. ビルド
npm run build
```

全て通らなければデプロイしない。

## Phase 6: デプロイ

1. git commit（変更内容を反映したメッセージ）
2. ご主人に push 確認
3. git push
4. Amplify / CI のビルド状況を確認

## スキップ条件

以下の場合はこのフローを簡略化してよい:

- **1-2行の修正**（typo、明らかなバグ fix）→ Phase 4-6 のみ
- **設計が既に確定済み**（ご主人が詳細仕様を提示）→ Phase 2-3 をスキップ可
- **テスト環境がない**プロジェクト → Phase 4 を手動検証に置き換え

## アンチパターン（やってはいけないこと）

1. **設計をセルフレビューで済ませる** → 必ずタヌキに投げる
2. **テストなしで実装を始める** → RED を確認してから GREEN にする
3. **ご主人の言葉をそのまま設計にする** → 専門家ペルソナで深堀りする
4. **Critical を無視して先に進む** → 設計を修正してから実装
5. **ビルド検証をスキップする** → 3つ全て通ってからデプロイ
